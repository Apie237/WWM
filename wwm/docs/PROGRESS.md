## Phase 6 — Authentication + Admin Foundation (completed 2026-10-15)

**Note on this record**: the Phase 6 implementation below was built in an earlier Claude Code terminal session; `CLAUDE.md`/`docs/PROGRESS.md` had not yet been updated to reflect it (still read "NEXT APPROVED PHASE" / unchecked). This session's job was exactly the scenario Phase 6's own instructions anticipated — "verify what is actually implemented, don't rely only on the documentation" — so before writing anything, every backend and frontend file was read and checked against `docs/PROJECT_SPEC.md` §14, `docs/CLAUDE.md`, and the Phase 6 instructions. It matched on every point. One real bug was found and fixed (below); the docs are now corrected to match the verified repository state.

**Backend — `User` model** (`server/src/models/User.js`): a new, separate Phase 6 model — deliberately not folded into `Person`, since a `User` is an admin/CMS login credential, not an organizational person record, and `PROJECT_SPEC.md` §6 lists `User` as its own "Administration model." Fields: `name`, `email` (unique), `passwordHash` (`select: false`, also stripped a second time by a `toJSON` transform so a stray `.select('+passwordHash')` elsewhere can never leak it through a normal response), `role` (enum, `ADMIN_ROLES` in `models/enums.js`: `SUPER_ADMIN`, `INTERNATIONAL_ADMIN`, `COUNTRY_ADMIN`, `CONTENT_EDITOR` — exactly the four from `PROJECT_SPEC.md` §14, no others), `country` (ref, only for `COUNTRY_ADMIN`), `isActive`, `lastLoginAt`, timestamps. A `pre('validate')` hook enforces the country-scope invariant at the schema level: a `COUNTRY_ADMIN` must have a `country`, and no other role may have one.

**JWT/cookie strategy**: the JWT is delivered as an **httpOnly cookie** (`wwm_admin_token`, `server/src/config/auth.js`), not a token the frontend stores itself — deliberately chosen over localStorage/sessionStorage so a successful XSS on the admin frontend cannot exfiltrate the session token (the "carefully consider XSS/security implications" instruction in Phase 6 §6). `secure`/`sameSite` are set appropriately for cross-origin cookies in production (client and server are separate Vercel deployments) vs. same-site `Lax` in local dev. A `Bearer` header is also accepted by the auth middleware as a secondary path, so the API stays testable from curl/Postman without a cookie jar. `JWT_SECRET` is required from the environment in production and only falls back to a random per-process value in development (never a hardcoded literal) — `server/src/config/env.js`.

**Routes/controllers/services** (Routes → Controllers → Services → Models, per `CLAUDE.md`):
- `POST /api/auth/login` (rate-limited: 10 attempts / 15 min / IP, `express-rate-limit`) — validates input shape in the controller, delegates to `authService.login()`. Returns the same "Invalid email or password." for a nonexistent email and a wrong password (no account-enumeration via login), a distinct 403 for a disabled account, and never returns `passwordHash`.
- `POST /api/auth/logout` — clears the cookie.
- `GET /api/auth/me` (`requireAuth`) — returns the authenticated admin.
- `GET /api/admin/dashboard` (`requireAuth`) — Phase 6 shell endpoint only; no CMS data.

**Authorization middleware** (`server/src/middleware/auth.js`): `requireAuth` (reads cookie or Bearer header → verifies JWT → re-checks `isActive` against the database on every request, not just at login, so a disabled admin loses access immediately without needing token revocation → attaches `req.admin`), `requireRole(...roles)`, and `requireCountryAccess(resolveCountryId)` — the country-scoping foundation from Phase 6 §9: `SUPER_ADMIN`/`INTERNATIONAL_ADMIN` pass through, a `COUNTRY_ADMIN` is only allowed through when `resolveCountryId(req)` (a caller-supplied, server-side lookup — e.g. resolving a `:country` slug against the database) matches their own assigned country. No country name is hardcoded anywhere in the authorization logic. This is foundation only, per the instructions — no Phase 7 route actually calls `requireCountryAccess` yet, since no country-scoped CMS routes exist yet.

**Admin seed** (`server/src/scripts/seedAdmin.js`, `npm run seed:admin`): creates/updates exactly one `SUPER_ADMIN` from `ADMIN_SEED_NAME`/`ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` environment variables; refuses to run if any are missing, enforces a minimum password length, and never falls back to a hardcoded default admin. Upserts by email, so it's safe to re-run.

**Frontend — admin foundation**: `AuthContext`/`useAuth` (`client/src/context/`, `client/src/hooks/useAuth.js`) centralize "is an admin signed in, who are they, still initializing?" in one place, backed by `services/authApi.js` (a separate `withCredentials: true` axios instance from the public `services/api.js` client, so the admin session cookie is never sent on public-site requests). `ProtectedRoute` (`components/admin/ProtectedRoute.jsx`) redirects an unauthenticated visitor to `/admin/login` (preserving the attempted location so login returns them there), and redirects an authenticated-but-wrong-role visitor to `/admin/unauthorized` — explicitly documented in-code as UI-only; the real security boundary is the backend middleware above. `AdminLayout`/`AdminSidebar`/`AdminHeader` form the admin shell (desktop: permanent left sidebar; mobile: off-canvas panel with focus trap, matching the public site's `MobileNavigation` pattern) — intentionally a separate shell from the public `Layout`, not the public header/footer. `AdminLogin`, `AdminDashboard` (shell only — calls the real protected `/api/admin/dashboard` endpoint to prove the full auth chain works, renders no CMS content), and `AdminUnauthorized` are implemented. Routes: `/admin/login`, `/admin/unauthorized`, `/admin` → `/admin/dashboard` (protected, wrapped in `ProtectedRoute`).

**Logo** (`client/assets/logo.55` → `client/src/assets/logo.55`): inspected with `file`/magic-byte detection per the Phase 6 §17 instruction rather than assumed from the extension — it is a genuine **WebP image** (`RIFF ... Web/P image`), not PNG/SVG/JPG. `vite.config.js` adds `assetsInclude: ['**/*.55']` so Vite treats the non-standard extension as a static asset, and renames the build output to `.webp` via `rollupOptions.output.assetFileNames` (confirmed in this session's verification build: `dist/assets/logo-*.webp`, itself a real WebP file) so browsers/CDNs resolve the correct content type — the source file's own path/extension is left untouched. One `Logo` component (`components/ui/Logo.jsx`) with a `showText`/`textClassName` prop is used consistently everywhere the mark appears: public `Header`, `Footer`, `MobileNavigation`, and admin `AdminSidebar`, `AdminLogin` — no duplicated image assets or bespoke logo markup anywhere.

**Vercel configuration**: `client/vercel.json` (`buildCommand`, `outputDirectory: dist`, and a `rewrites` catch-all to `index.html` for React Router's client-side routes — confirmed in this session against the actual `vite build` output directory) and `server/vercel.json` (`@vercel/node` build of `api/index.js`, rewriting everything to it) both already existed and were inspected rather than recreated, per the instruction to improve existing config rather than duplicate it. **One real bug was found and fixed in this session**: `server/api/index.js` registered its lazy per-request `connectDB()` middleware with `app.use()` *after* `createApp()` had already attached its terminal `notFound`/`errorHandler` handlers — meaning that middleware could never actually run for any request (Express executes middleware in registration order; nothing registered after a terminal handler in the stack is reached). Fixed by wrapping the already-built Express app in a plain `(req, res)` handler function that calls `connectDB()` first and then delegates to the app — `@vercel/node` accepts a plain handler function just as it accepts an Express app, so this needed no change to `src/app.js` or the local dev entry point (`src/index.js`, unaffected). No root `vercel.json` was created, since the client and server are genuinely separate deployable projects.

**Environment variables added**: `server/.env.example` already had `JWT_SECRET`, `JWT_EXPIRES_IN`, and `ADMIN_SEED_NAME`/`ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` (all placeholders, no real values) — confirmed present and correctly placeholder-only in this session. `client/.env.example` already correctly had only `VITE_API_URL` — no server-only secret is exposed through a `VITE_` variable.

**Verification performed (this session)**: `npm audit fix` applied cleanly to both `client` and `server` (lockfile-only changes, no dependency version bumps, `0 vulnerabilities` afterward in both). `npm run build` passes for the client (`dist/assets/logo-*.webp` confirmed a real WebP via `file`); `npm run lint` (oxlint) shows only the same pre-existing benign `set-state-in-effect` warnings already accepted in Phases 4–5 — no new warning categories from any Phase 6 file. Standalone checks confirmed `bcryptjs` hashing/comparison and, using the project's own `authService.signAdminToken`/`verifyAdminToken`, that JWT generation and verification (including rejection of a tampered token) work correctly. With the Express server running: `/api/health` returns 200; existing public routes (e.g. `/api/continents`) remain reachable and unauthenticated, correctly surfacing the same pre-existing Mongoose buffering-timeout (no local MongoDB in this sandbox — the identical, already-documented Phase 4/5 environment condition; an attempt to spin up an in-memory MongoDB via `mongodb-memory-server` this session was blocked by the sandbox's network allowlist, consistent with that same limitation) rather than a routing error; `GET /api/auth/me` and `GET /api/admin/dashboard` both correctly return 401 with no credential; `POST /api/auth/login` correctly returns 400 for an invalid email format and for a missing password (validated before any DB access); the login rate limiter was exercised directly and correctly began returning 429 once the 15-minute/10-attempt budget was spent; CORS correctly reflects `Access-Control-Allow-Origin`/`-Credentials` for the configured client origin; an unknown route still returns the existing 404 handler's JSON shape. ## Phase 7 — CMS CRUD (completed 2026-10-15)

**Scope**: full list/view/create/edit/delete/search/filter/pagination CRUD for the eight approved modules — Continents, Countries, People, Country Administration, Affiliate Pastors Boards, Churches, Institutions, Ministries (the last two both map to the single `Organization` model, per `docs/CLAUDE.md`'s "Country Architecture" rule — there is one Organizations admin module with a `type` filter, not two). News/events, prayer requests, resources/documents, Cloudinary, payment systems, new auth providers, and public-site redesigns were explicitly out of scope and were not touched. The Phase 6 foundation (JWT/cookie auth, bcrypt, the four admin roles, `requireAuth`/`requireRole`/`requireCountryAccess`, admin shell, DB connection handling, Vercel entry point, public API) was preserved as-is — nothing in it was rebuilt or replaced.

**Backend — shared helpers** (`server/src/utils/adminHelpers.js`, new): `pickAllowed` (mass-assignment whitelist), `requireObjectIdParam`/`requireObjectIdField` (400 instead of an uncaught `CastError`), `isDuplicateKeyError`/`duplicateKeyMessage` (E11000 → safe 409), `assertCountryWritable`/`scopeFilterToCountry`/`canManageCountry` (every `COUNTRY_ADMIN` check reads only `req.admin` from the verified JWT, never a client-submitted id), and `applySearch` (a regex-escaped, case-insensitive `?search=` filter shared by every list endpoint that exposes one).

**Backend — seven admin modules**, each following Routes → Controllers → Services → Models with a thin controller, business/authorization logic in the service, and Mongoose concerns only in the model (no model changes were needed — Phase 2's models already supported everything Phase 7 needed):
- **Continents** (`services/controllers/routes/admin/continents.js`) — full CRUD; writes restricted to `SUPER_ADMIN`/`INTERNATIONAL_ADMIN` (continents are international-level structure, not country-scoped); delete blocked while any `Country` still references it.
- **Countries** (`.../countries.js`) — full CRUD; a `COUNTRY_ADMIN` may edit only their own country's descriptive content (`overview`, `flagImageUrl`, `contact` — `COUNTRY_CONTENT_ONLY_FIELDS`), never its name/slug/continent/order/active status (`COUNTRY_WRITABLE_FIELDS`, documented ambiguity resolved this way per the "content vs. structural" role matrix below); create/delete restricted to `SUPER_ADMIN`/`INTERNATIONAL_ADMIN`; delete blocked while any Country-Administration, Affiliate-Pastors-Board, Organization, Person-role, or Ministry record still references it.
- **People** (`.../people.js`) — full CRUD; `roles[].roleType`/`country`/`organization` are all validated against real enum values and existing records before save; a `COUNTRY_ADMIN` may only see/create/edit people all of whose roles are in their own country (enforced via a `roleCountryId` normalizer that handles both populated and unpopulated `role.country`); delete blocked while any Organization leader, Ministry responsible-person, or administration/board-member entry still references this person.
- **Organizations** (churches + institutions, `.../organizations.js`) — full CRUD, `type`/`country`/`search` filters; `leaders[].person` validated to exist; a `COUNTRY_ADMIN` is confined to their own country on every operation, including rejecting an attempted re-assignment to a different country on update; delete blocked while any Ministry or Person role still references it.
- **Ministries** (`.../ministries.js`) — full CRUD, `ministryType`/`country`/`search` filters; a `COUNTRY_ADMIN` must always supply (and can never change away from) their own country — an international-scope (country-less) ministry is out of their reach entirely, same as one belonging to another country; no delete guard needed (nothing in the schema references a Ministry by id).
- **Country Administration** (`.../countryAdministrations.js`) — document-level CRUD (`current`/`historical`/`effectiveFrom`/`effectiveTo`/`notes`) plus entry-level sub-resource endpoints (`POST/PATCH/DELETE /:id/positions[/:entryId]`) for the self-referencing `positions` hierarchy, which sidesteps the chicken-and-egg problem of a client needing a server-assigned entry id before it can reference it as another entry's `parentEntry`. `assertNoCycle` walks `parentEntry` pointers upward (bounded by array length) to reject a reporting-line cycle; removing an entry that others still report to is rejected with a 409 until they're reassigned or removed first. This is governance/organizational data, not "content," so `CONTENT_EDITOR` gets read-only access here (unlike People/Organizations/Ministries) — the documented resolution of the task's "if ambiguous, document rather than silently grant" instruction.
- **Affiliate Pastors Boards** (`.../affiliatePastorsBoards.js`) — identical shape and rules to Country Administration, with `members` in place of `positions`; implemented as its own small service/controller/route trio rather than folded into the Country Administration files, matching the project's existing treatment of the two as separate (if structurally similar) models with their own public controllers/services already.

**Authorization matrix actually enforced** (documented in-code at each module's route file): `SUPER_ADMIN` — full access everywhere. `INTERNATIONAL_ADMIN` — same as `SUPER_ADMIN` on every Phase 7 module (no module in this phase is `SUPER_ADMIN`-exclusive). `COUNTRY_ADMIN` — reads/writes/deletes scoped strictly to their assigned country on Countries (content fields only)/People/Organizations/Ministries/Country Administration/Affiliate Pastors Boards; no access to Continents (not country-scoped at all). `CONTENT_EDITOR` — read+write (no delete) on People/Organizations/Ministries ("content"); read-only on Continents/Countries/Country Administration/Affiliate Pastors Boards ("structural/governance"); this content-vs-structural split is the explicit resolution of the task's documented ambiguity, chosen over silently granting `CONTENT_EDITOR` any additional privilege.

**Frontend — service layer** (`client/src/services/adminApi.js`, new): one `crud(resource)` factory producing `list/get/create/update/remove` against `/api/admin/<resource>`, built on the existing `authApi` (Phase 6) axios instance so the httpOnly session cookie is sent automatically; `countryAdministrationsApi`/`affiliatePastorsBoardsApi` additionally expose their position/member sub-resource calls. `isHttpStatus`/`errorMessage` mirror the existing public `services/api.js` conventions.

### Phase 7 — targeted security-review corrections (2026-10-15)

A follow-up review found that Phase 7's record-level `COUNTRY_ADMIN` authorization (confining which *document* an admin may touch) did not also confine the *references that document points at* — a permitted record could still reference a leader, responsible person, board member, or organization belonging to a different country, purely because that id existed somewhere in the database. This pass closes that gap without touching the rest of Phase 7's implementation, Phase 6's authentication foundation, or any Phase 2 model.

**`server/src/utils/adminHelpers.js`** gained two shared relationship checks — `assertPersonBelongsToCountry` (a person must hold at least one role whose `country` matches the target country, or an internationally-scoped role with no country at all, which is accepted for any country so legitimate international people/admins are never blocked) and `assertOrganizationBelongsToCountry` (an organization's own `country` must match) — plus `requireValidObjectIdListField`, which validates every id in an array-of-references field (leaders, responsible people, role country/organization ids) *before* any of them reach a Mongoose `$in` query, so a malformed id is a `400` instead of an uncaught `CastError` (`500`).

- **Organizations** (`organizationAdminService.js`): `validateLeaders` now checks every leader's `person` against the organization's own (effective, post-save) country; updating a different field while leaving `country` unchanged re-validates the existing leaders instead of assuming they're still valid.
- **Ministries** (`ministryAdminService.js`): `validateResponsiblePeople` gets the same per-person country check (skipped only when the ministry itself is internationally scoped — the one relationship the model explicitly allows to cross a country boundary, since there is then no single country to compare against); a new `organization`/`country` cross-reference check rejects a ministry whose organization belongs to a different country; `updateMinistryAdmin` re-derives the *effective* country/organization/responsible-people (resent or not) so changing a ministry's country can never silently leave an now-invalid cross-country organization or person behind.
- **People** (`personAdminService.js`): `validateRoles` now rejects a role that names both a `country` and an `organization` when that organization actually belongs to a different country ("role in Kenya, organization in Nigeria"); a role naming only an organization (no country) is left unchecked, since it declares no country to be inconsistent with.
- **Country Administration / Affiliate Pastors Board** (`countryAdministrationAdminService.js`, `affiliatePastorsBoardAdminService.js`): `assertPersonExistsIfSet` now also calls `assertPersonBelongsToCountry` against the document's own country for every position/member `person`, so a `COUNTRY_ADMIN` can no longer fill their own country's leadership structure with a person who has no actual connection to it. The existing cycle-detection and child-reassignment-required delete guards were left untouched.

These checks run for every caller (not only `COUNTRY_ADMIN`) because they are data-integrity rules, not permission checks — combined with the existing, unmodified record-level `assertCountryWritable`/`scopeFilterToCountry`, they are what actually stops a `COUNTRY_ADMIN` from reaching across a country boundary through a *reference* instead of the record itself, while an internationally-scoped person/role/ministry remains fully usable by `SUPER_ADMIN`/`INTERNATIONAL_ADMIN` exactly as before.

**Tests**: no test framework or test files existed anywhere in this project before this pass (confirmed by inspection), so `node --test` (Node 22's built-in runner — zero new dependencies, no lockfile change) was added as `npm test` in `server/package.json`, together with `server/src/__tests__/phase7RelationshipAuthorization.test.js` — 25 tests across 7 suites, all passing, directly exercising the corrected functions above (with `Person`/`Organization`/`Country` model methods mocked, since no MongoDB is reachable in this sandbox — see the limitation already recorded above). Covered: a `COUNTRY_ADMIN` cannot assign a leader/responsible-person/board-member from another country; a ministry cannot reference another country's organization; a role cannot pair a country with a mismatched organization's country; malformed reference ids return `400` instead of a `CastError`; valid-but-nonexistent references still return a clear validation error; and an internationally-scoped person/role is accepted for any country, preserving legitimate cross-country relationships for authorized administrators. `node --check` was re-run against every file in `server/src` (all pass) and the full Express app was rebooted and its route tree re-dumped to confirm nothing else changed.

**Remaining limitation**: the same "no MongoDB reachable in this sandbox" limitation applies here too — these are mocked unit tests of the corrected validation logic itself, not a database-backed integration run. A real DB-backed pass (an actual `COUNTRY_ADMIN` login attempting each of the blocked cross-country assignments against live data) is recommended once a reachable MongoDB instance is available, same as already recommended for the rest of Phase 7.

## Phase 9 — Media Management & Cloudinary (implemented 2026-10-16)

**Scope**: authorized admins can upload JPEG/PNG/WebP images to Cloudinary from the existing CMS forms for the four fields that already held an image URL: `News.imageUrl`, `Event.imageUrl`, `Person.photoUrl`, `Country.flagImageUrl`. Organization, Ministry and Resource have no image field, so none was added. Document/PDF uploads for Resources are deferred (they would need a document model).

**Design**: no Cloudinary SDK and no new dependency — the server calls Cloudinary's signed REST API with built-in `fetch`/`FormData`/`crypto`. No `Media` model: each owning record stores a companion public-id field (`imagePublicId`, `photoPublicId`, `flagImagePublicId`) next to its URL. Upload is server-proxied (raw request body, default max 4 MB via `MEDIA_MAX_UPLOAD_MB`, to fit Vercel's body limit). Public IDs must match `wwm/<news|events|people|countries>/<32 hex>` and the kind must match the target module; the stored URL is rebuilt server-side from the ID.

**Endpoints**: `GET /api/admin/media/config` (limits only), `POST /api/admin/media/upload/:kind` (auth + per-admin rate limit 60/h + role per kind). There is no delete-by-ID endpoint.

**Safety rules**: magic-byte check (must agree with declared type); 503 when Cloudinary is not configured (before the body is read); generic 502 on upstream failure with no upstream detail or secret returned or logged; an asset referenced by another record cannot be attached (409); Cloudinary deletion only happens after the DB write succeeds and only if no record still references the asset, and it is best-effort; country scope is enforced by the owning module's existing ownership checks; pre-Phase-9 legacy URLs keep working.

**Frontend**: `ImageUpload` admin component (preview, uploading %, client-side type/size checks, replace, remove, errors; falls back to a plain link input when uploads are not configured) used in the News, Event, Person and Country forms. Public pages request width-limited renditions via `lib/images.js` (`srcset` on news images).

**Verification (actual)**: `npm test` (server) — 96 tests, 96 pass (56 prior + 40 new in `phase9Media.test.js`, Cloudinary mocked at the fetch layer; includes Cloudinary's published signature test vector). Client `npm run build` passes; `npx oxlint` shows no errors in the new or changed code (remaining warnings are the previously accepted set-state-in-effect category).

**Not verified / limitations**: the live Cloudinary integration was NOT tested (no credentials or network) — only the mocked API. No MongoDB was reachable, so nothing ran against a real database. The admin upload control was compiled and linted but not exercised in a browser against a real session. Uploaded-but-never-attached assets stay orphaned (no sweeper). No live existence check when attaching an ID. No alt-text field exists on the models. Behind a proxy Express `trust proxy` is needed for IP-based limits on the Phase 8 public forms.
